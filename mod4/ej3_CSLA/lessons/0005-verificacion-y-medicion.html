Lección 5 · Ejercicio 3 — Carry Select Adder

Verificación y medición: tb_csla.sv y run.sh

Vas a correr bash run.sh delante del profesor. Esta lección te prepara para explicar qué hace cada parte de la salida: la verificación funcional, el cross-check, la medición de delay y el conteo de gates con Yosys.

Ejercicio 3

El objetivo de esta lección

Al terminar vas a poder explicar cómo se sabe que el CSLA suma bien y de dónde salen los 16 ns y los 200 gates de la tabla. La clave del enfoque: el testbench es self-checking — nadie mira formas de onda, el testbench compara contra un modelo de referencia y reporta PASS/FAIL.

1. La estrategia en tres capas

El testbench no tira 1500 vectores a lo loco: verifica en tres niveles, de lo más chico a lo más grande:

CapaQué verificaVectores
[1/3] rca4 exhaustivola célula del CSLA512 (256 × cin)
[2/3] csla16 bordeslos casos límite4
[3/3] csla16 randomel sumador completo1000

2. La célula: rca4 exhaustivo

for (i = 0; i < 256; i = i + 1) begin
  apply_rca4("exhaustivo", i[3:0], i[7:4], 1'b0);
  apply_rca4("exhaustivo", i[3:0], i[7:4], 1'b1);
end

El truco: con i recorriendo 0…255, i[3:0] da a y i[7:4] da b — así se barren las 256 combinaciones de (a,b) de 4 bits en un solo loop. Y cada una se prueba con cin=0 y cin=1: 512 vectores. Para 4 bits esto es barato (los 4 bits de a y b); para el CSLA de 16 bits ya no sería viable (2³²), por eso ahí se usa random.

La referencia no es el DUT: el testbench calcula expected4 = va + vb + vcin con el operador + de SystemVerilog y compara. Un sumador "de oro" independiente.

3. Los bordes del csla16

apply_and_check("0+0",     '0, '0, 1'b0);
apply_and_check("max+max", '1, '1, 1'b0);   // carry-out = 1
apply_and_check("max+cin", '1, '0, 1'b1);   // carry-out = 1
apply_and_check("max+1",   '1, 1, 1'b0);    // sum=0, cout=1

Los bordes son los casos donde más fácil es equivocarse: 0+0 (todo ceros), max+max (todo unos → desborda), max+cin y max+1 (la suma da 0 con carry-out 1). Son los cuatro vectores "didácticos" del enunciado del ejercicio 1, reciclados acá.

4. Random + cross-check: la parte ingeniosa

for (i = 0; i < NRAND; i = i + 1)
  apply_and_check("random", $urandom(seed), $urandom(seed), $urandom(seed) & 1'b1);

Dos decisiones importantes:

  • Semilla fija (seed = 2026): $urandom(seed) con semilla genera la misma secuencia cada vez que se corre. La verificación es reproducible: si pasa hoy, pasa siempre. Un random sin semilla no te dejaría "mostrar que siempre pasa".
  • Cross-check: además de comparar contra expected = a + b + cin (el modelo de oro), el testbench instancia tres sumadores más — RCA16, CLA16 v1 y CLA16 v2 — estimulados con lo mismo, y exige que los cuatro coincidan:
expected = va + vb + vcin;
if ((sum_csla !== expected[15:0]) || (cout_csla !== expected[16])) errors++;// vs. modelo
if ((sum_csla !== sum_rca)     || (cout_csla !== cout_rca))    errors++;   // vs. RCA
if ((sum_csla !== sum_cla)     || (cout_csla !== cout_cla))    errors++;   // vs. CLA v1
if ((sum_csla !== sum_cla_v2)  || (cout_csla !== cout_cla_v2)) errors++;   // vs. CLA v2

Cuatro sumadores implementados de formas completamente distintas (ripple, lookahead, y el propio CSLA) no pueden coincidir en 1000 vectores por casualidad si uno estuviera mal. Es una red de seguridad extra sobre el modelo de oro. El testbench espera #(2*N16 + 5) = 37 ns entre vector y vector: suficiente para que el más lento (el RCA, 32 ns) estabilice.

5. La medición de delay

El delay se mide por simulación con los delays del modelo de compuertas, no por análisis estático. La técnica:

always @(cout_csla)     t_last_csla_cout = $time;   // monitor del carry-out
always @(sum_csla[15])  t_last_csla_sum  = $time;   // monitor del bit de suma

Los monitores "anotan" cada vez que cambia la salida. El paso de medición:

  1. Se estabiliza el estado previo (0,0,0) y se captura t0.
  2. Se aplica el peor caso: a='1, b=1, cin=0 → 0xFFFF + 1. El bit 0 genera carry y tiene que recorrer los 16 bits.
  3. Se espera a que t_last cambie y se calcula delay = t_last − t0.

Se miden dos salidas por arquitectura: cout (el carry que recorre todo) y sum[15] (el bit de suma más significativo). Son caminos distintos: sum[15] pasa por los muxes de suma, cout por los muxes de carry.

6. El conteo de gates (área)

El área no se mide: se estima contando compuertas. El testbench define el costo de cada célula (FA = 5 gates, mux2 = 4, cla4 = 35) y deriva el total con fórmulas estructurales:

GATES_CSLA = GATES_RCA4 + 3 * (2 * GATES_RCA4 + 5 * GATES_MUX2);   // = 200

O sea: bloque 0 (1 rca4) + 3 bloques × (2 rca4 + 5 muxes). Pero un conteo "de memoria" no alcanza para convencer: run.sh lo verifica contra el netlist real:

sanitize() { sed -E '/localparam time/d; s/#\([^)]*\)//g' "$1"; }   // Yosys no acepta
                                                                     // delays ni localparam time
count_gates() {
  yosys -p "read_verilog -sv ...; hierarchy -top $1; flatten; techmap; stat" \
    | awk '/Number of cells/{print $NF}'
}

Yosys sintetiza el diseño a compuertas primitivas, aplanado, y cuenta las celdas. Las cuatro arquitecturas deben dar el mismo número que el cálculo estructural:

CSLA16     yosys= 200 manual= 200  OK
CLA16 v1   yosys= 140 manual= 140  OK
CLA16 v2   yosys= 167 manual= 167  OK
RCA16      yosys=  80 manual=  80  OK

Nota de detalle: a Yosys hay que pasarle una copia "sanitaria" de las fuentes porque no acepta localparam time ni los delays #(...) — esos se quitan con sed porque solo sirven para la simulación, no para contar lógica.
