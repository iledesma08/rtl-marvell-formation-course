Ejercicio 3

El objetivo de esta lección

Al terminar vas a poder recorrer csla16.sv de arriba a abajo sin errores: qué son las señales internas, por qué el bloque 0 está fuera del generate, qué hace a[i*4 +: 4], y por qué el mux se arma con compuertas. Tené los dos archivos abiertos mientras leés.

1. El mapa del módulo

El archivo csla16.sv define dos módulos: csla16 (el sumador completo) y mux2 (el mux 2:1 estructural que usa). El orden no importa para la simulación, pero conviene mostrarlo así.

module csla16 (
  input  logic [15:0] a,        // operando A (16 bits)
  input  logic [15:0] b,        // operando B
  input  logic        cin,      // carry de entrada externo
  output logic [15:0] sum,      // suma
  output logic        cout      // carry de salida
);

2. Las señales internas

logic [4:0] cblk;              // carry por bloque: cblk[0]=cin, cblk[4]=cout
logic [3:0] sum0 [1:3];        // resultado del bloque i con cin=0
logic [3:0] sum1 [1:3];        // resultado del bloque i con cin=1
logic       cout0 [1:3];       // carry del bloque i con cin=0
logic       cout1 [1:3];       // carry del bloque i con cin=1

assign cblk[0] = cin;          // el primer carry es el externo

Las claves:

  • cblk es un vector de 5 bits: cblk[0] = cin, cblk[4] = cout, y los del medio son los carries entre bloques. Es la "columna vertebral" del sumador.
  • sum0 [1:3] es un arreglo no empaquetado (unpacked array): tres elementos —bloques 1, 2 y 3— y cada elemento es un vector de 4 bits. No existe sum0[0]: el bloque 0 no especula. Por eso el rango va de 1 a 3.
  • cout0/cout1 son arreglos de un bit por bloque, para el carry especulativo.

3. El bloque 0, afuera del generate

rca4 u_blk0 (
  .a   (a[3:0]),
  .b   (b[3:0]),
  .cin (cblk[0]),        // usa el cin real, no especula
  .sum (sum[3:0]),
  .cout(cblk[1])         // su carry-out gobierna el mux del bloque 1
);

Un solo RCA, sin mux. Es el único bloque que conoce su carry de entrada desde el principio.

4. El generate de bloques especulativos

genvar i;
genvar k;
generate
  for (i = 1; i < 4; i = i + 1) begin : sel_blocks
    rca4 u_rca0 (
      .a   (a[i*4 +: 4]),
      .b   (b[i*4 +: 4]),
      .cin (1'b0),
      .sum (sum0[i]),
      .cout(cout0[i])
    );
    rca4 u_rca1 (
      .a   (a[i*4 +: 4]),
      .b   (b[i*4 +: 4]),
      .cin (1'b1),
      .sum (sum1[i]),
      .cout(cout1[i])
    );
    ...
  end
endgenerate
  • genvar + generate: el loop no se ejecuta en simulación; se "desenrolla" en tiempo de elaboración. Cada iteración crea instancias reales con nombres jerárquicos (p. ej. sel_blocks[1].u_rca0).
  • Bloque con nombre (begin : sel_blocks): obligatorio en el generate-for. Da el nombre de la jerarquía y permite referirse a señales dentro.
  • Los dos RCAs son idénticos salvo el cin: 1'b0 en u_rca0, 1'b1 en u_rca1. Esa es la especulación: misma entrada, distinta suposición.

5. El part-select a[i*4 +: 4]

Para que el bloque i tome sus 4 bits de a, se escribe a[i*4 +: 4]: "4 bits hacia arriba empezando en i*4".

i=0 → a[0 +: 4] = a[3:0]
i=1 → a[4 +: 4] = a[7:4]
i=2 → a[8 +: 4] = a[11:8]
i=3 → a[12 +: 4] = a[15:12]

Es un indexed part-select. La ventaja sobre escribir a[i*4 + 3 -: 4] o calcular rangos a mano: el índice base se calcula en el generate y el +: 4 siempre "va para arriba", evitando errores de límite. Mismo patrón en rca4.sv y en los cla16 del ejercicio 2.

6. Los muxes de suma (generate interno)

for (k = 0; k < 4; k = k + 1) begin : sum_mux
  mux2 u_mux_s (
    .sel (cblk[i]),        // carry del bloque ANTERIOR
    .d0  (sum0[i][k]),     // resultado suponiendo cin=0
    .d1  (sum1[i][k]),     // resultado suponiendo cin=1
    .y   (sum[i*4 + k])    // bit de suma definitivo
  );
end
  • Como mux2 es de 1 bit, se instancian 4 muxes por bloque (uno por bit de suma) con un segundo generate anidado en k.
  • La convención de conexión es la clave: d0 recibe la versión cin=0 y d1 la versión cin=1, porque mux2 elige d1 cuando sel=1. Si cblk[i]=0, la respuesta correcta era la del RCA con cin 0.

7. El mux del carry

mux2 u_mux_c (
  .sel (cblk[i]),
  .d0  (cout0[i]),         // carry-out si cin era 0
  .d1  (cout1[i]),         // carry-out si cin era 1
  .y   (cblk[i + 1])       // carry real hacia el siguiente bloque
);

El carry-out del bloque también depende de cuál suposición era correcta, así que se selecciona con otro mux del mismo tipo. El resultado alimenta cblk[i+1], que a su vez es el sel del bloque siguiente: por eso el carry "salta" de bloque en bloque por los muxes.

8. El mux2 estructural

module mux2 (
  input  logic sel, d0, d1,
  output logic y        // y = (d0 & ~sel) | (d1 & sel)
);
  localparam time TAND = 1ns;
  localparam time TOR  = 1ns;
  localparam time TNOT = 1ns;

  not #(TNOT) u_not (sel_b, sel);
  and #(TAND) u_and0 (t0, d0, sel_b);
  and #(TAND) u_and1 (t1, d1, sel);
  or  #(TOR)  u_or   (y, t0, t1);
endmodule

El mux es la ecuación y = (d0 & ~sel) | (d1 & sel) hecha compuertas. Los caminos de delay:

  • sel → y: 3 ns (not + and + or). Es el camino del carry entre bloques.
  • d0/d1 → y: 2 ns (and + or). Es el camino de las sumas especulativas (que ya estaban listas).

Preguntas típicas del profesor

  • "¿Por qué el mux es estructural y no assign y = sel ? d1 : d0?" Para que la medición de delay sea consistente con el modelo de compuertas de los ejercicios 1 y 2 (xor=2ns, and/or/not=1ns). Un mux comportamental sintetizaría a otra cosa y el path crítico no sería comparable.
  • "¿Por qué sum0 es un arreglo y no 6 señales sueltas?" Porque el generate necesita indexar por bloque: sum0[i] con i genvar.
  • "¿Y si querés bloques de 8 bits?" Cambiás el tamaño de rca4 (o usás rca parametrizado), el for del medio de k a 8, y el rango de bloques a N/8. La estructura no cambia.
  • "¿El bloque 0 podría ser especulativo también?" No aportaría nada: su cin se conoce al inicio, no hay nada que esperar.
